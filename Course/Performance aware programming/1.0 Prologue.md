## IPC

this is was an introduction about the IPC(instructions per clock) and ILP(instruction level parralelism) metrics.
How with the difference in execute different loops, we can improve the work done per cycle and hence improve the performance.
ILP is the combination of the instructions done by the CPU which are not related.

As an example this two work differently based on how many compares are done + how many add instructions are not depended on each other, a much simpler form of batching

	}

typedef unsigned int u32;
u32 Unroll2Scalar(u32 Count, u32 *Input)
{
	u32 Sum = 0;
	for(u32 Index = 0; Index < Count; Index += 2)
	{
		Sum += Input[Index];
		Sum += Input[Index + 1];
	}
	
	return Sum;
}

```

1.7 adds per cycle

typedef unsigned int u32;
u32 QuadScalarPtr(u32 Count, u32 *Input)
{
	u32 SumA = 0;
	u32 SumB = 0;
	u32 SumC = 0;
	u32 SumD = 0;
	
	Count /= 4;
	while(Count--)
	{
		SumA += Input[0];
		SumB += Input[1];
		SumC += Input[2];
		SumD += Input[3];
		Input += 4;
	}
	
	u32 Sum = SumA + SumB + SumC + SumD;
	return Sum;
}
```

## SIMD

this stands for single instruction multiple data, this is the another form of reduction of the instruction set given to the CPU
eventually the accumulators in the previous section have the same problem
the instructions would stack up. the concept is simple that instead on iterating on a single piece of data in a instructions , we add multiple data

this becomes the paddd inst,
The “p” prefix stands for “packed”, because we are “packing” multiple pieces of data together to operate on. The “d” suffix stands for “DWORD”, which means 32-bits in this case, which is the size of the integer we are trying to add. And otherwise, it’s just “add” like it was before.
```

typedef unsigned int u32;
u32 __attribute__((target("ssse3"))) SingleSSE(u32 Count, u32 *Input)
{
	__m128i Sum = _mm_setzero_si128();
	for(u32 Index = 0; Index < Count; Index += 4)
	{
		Sum = _mm_add_epi32(Sum, _mm_load_si128((__m128i *)&Input[Index]));
	}

	Sum = _mm_hadd_epi32(Sum, Sum);
	Sum = _mm_hadd_epi32(Sum, Sum);
	
	return _mm_cvtsi128_si32(Sum);
}
```

this gives around 3 adds/cycle

## Cache

one of the multipliers missed in the previous discussions is how the data is load for the ADD instructions, because it all comes down to how quickly the data can be loaded for the cpu to process the instructions

namely, CPU cores have the L1 and L2 cache closest for itself but the sizes are restricted to 32KB or 256KB 
After which goes to L3 cache which is around 8MB, post which it goes to the RAM which is in GBs

forcing the program to each cache forces the performance down quickly


## Multithreading

multitasking is one of the best ways to utilize the modern CPUs. Current gen CPUs come with atleast 4 cores. These cores are capable of running their own instruction stream with different L1 and L2 cache for each core.

By dividing the work for different threads to pickup the different parts of it we ensure that different cores handle the load, and hence technically can fit 4x the workload managed by the L1 or L2 Cache.

thread is the OS level mechanism to assign the workload to the core which is the hardware level mechanism

so if instead of 4096 integers if divide 4096 * 4 among for thread we should see atleast 4x improvement in the adds per clock

single 4096 set of integers when divided among 4 threads, might perform much better but not as expected due to the overhead of opening / maintaining / closing the threads. hence the concept of partial or nonperformative threading as well
